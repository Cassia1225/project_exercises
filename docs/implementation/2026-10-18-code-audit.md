# 花粉対策ナビ 現行コード確認と段階別の修正点

確認日：2026-10-18（日本時間）／記録：綾華

## 1. 今回確認した範囲

UI、通信制御、受信処理、気象/花粉の取得・送信、推薦処理、AIアダプター、既存テスト、依存関係、README、最新のローカル設計書を読んだ。実API、DB、外部Brokerへの接続は行っていない。

作業ブランチは`Test`。既存の未コミット変更は`recommend/recommend.py`の本人の学習用コメントであり、維持する。`docs/`も未追跡である。ローカル設計書は題名・作成者が本人により編集されているため、Notionの旧コピーから上書きしない。

## 2. 修正前のコードの流れ

1. UIは`get_recommendation(location, date_label, allergies)`を読み込もうとする。この関数は現在の推薦モジュールにないため、ImportError時のダミー表示へ進む構成である。
2. 通信制御の`process_request()`は、入力検証→DBへ保存→MQTTで依頼を1回送信→受付結果を返す。取得結果の受信・集約・推薦・UIへの結果返却は未接続。
3. 気象/花粉の送信ファイルは起動時にAPIを取得し、固定Topicへ1回送信する。Controllerの要求を待ち受けるWorkerではない。
4. 気象受信は固定Topicを購読して値を表示する。送信側と受信側で気温・湿度のキーが一致していない。
5. 推薦関数は渡された値からレベルと対策を作る。外部APIの取得は行わず、AIはadvisor引数がある場合だけ呼ぶ。

過去の記録とは異なり、現在の環境では上記の通常実行でも収集・実行できた。PYTHONPATHを指定した再確認も31件成功したため、import問題を今回の新規不具合と断定して修正しない。

## 5. 段階的な実装順序

1. **レベル判定の基礎**：数値をUPIとして分類し、風・設定一致による加点を外す。小さい変更から始める。
2. **種類別判定と共通データ**：設定種の最大値、欠測、一般/個人の区別、1.2-draftの要求/返却を固定JSONで確認する。
3. **外部APIアダプター**：気象・花粉を偽HTTPで個別確認する。固定座標/日付、単位、公式応答、失敗処理を修正する。
4. **MQTTの要求・返信**：最初は架空JSONでWorker、検索ID、期限、重複・不一致を確認する。
5. **Controllerの集約**：DBを必須としない入口へ改め、取得→集約→推薦→結果返却を確認する。独立起動とHTTP境界は先に合意する。
6. **UI・地域・設定保存**：候補検索、現在地、検索操作、正規レスポンス表示、ブラウザー保存/復元/削除を確認する。
7. **全体の実取得・実演**：実APIを個別に確認した後、全体を接続する。複数PCの授業条件もここまでに確認する。
8. **任意の将来Gemini**：ルールのみで動く状態を確認してから追加する。

今回詳細化した実装計画は第1段階だけである。後続の実装計画は、その段階で最新コードと前段階の結果を確認して作る。全段階を今回一度に変更しない。


## 6. 第1段階の実装結果（2026-10-18）

C-01のUPI分類とC-02の風/設定一致による加点を修正した。UPIは0〜1低、2〜3中、4高、5非常に高い。通常の範囲外・非整数・bool・非有限値に加え、変換できない巨大整数も入力エラーとして返す。

修正前に失敗するテストを確認し、最終的に96件が合格した。別担当による差分レビューを行い、そこで指摘された巨大整数の例外漏れにも回帰試験を追加して修正した。対話式DBスクリプトと依存環境は試験収集から除外している。

C-03以降の種類別判定、欠測/partial、1.2-draft、DB不要のController、実MQTT/実API、UI/ブラウザー保存は未実装のままである。第1段階の合格をシステム全体の完成と扱わない。アプリの変更は推薦本体とそのテストのみで、本人の既存編集を維持し、コミット・pushはしていない。
