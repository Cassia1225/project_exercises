# 花粉対策ナビ：コードを読む順番

現在のアプリ全体を、起動から画面表示まで順に理解するための案内。

## 1. 最初に押さえる全体像

このアプリは、1つのPCで複数のPythonプログラムを動かす。

- UI：入力と結果表示。Streamlitを使う。
- 通信制御（Controller）：画面から依頼を受け、取得結果をまとめる。
- 気象：天気・風速などを取得する。
- 花粉：種類別の花粉指数を取得する。
- 推薦：花粉の対策レベルと対策文を決める。
- MQTT Broker：通信制御と取得担当の間で、メッセージを中継する。

画面→通信制御、通信制御→推薦はHTTP。通信制御→気象・花粉の要求と返信はMQTT。
HTTPもMQTTも、今回は同じPCの中で通信する。

## 2. 起動：run.py

`python run.py --demo`を実行すると、次の順で起動する。

```text
MQTT Broker
    ↓
気象担当
    ↓
花粉担当
    ↓
推薦担当
    ↓
通信制御担当
    ↓
画面
```

「起動する順番」と「検索時にデータが流れる順番」は異なる。

`run.py`の末尾から`main()`が呼ばれる。`main()`は起動オプションと設定を読み、ポートを確認する。`launch_plan()`が実行するプログラムの一覧を作り、`Supervisor`が1つずつ起動・起動確認する。Ctrl+Cでは、今回起動したプログラムをまとめて止める。

`--demo`では気象・花粉を架空データにする。ただしHTTP/MQTTは実際に通信し、地域一覧の読み込み・現在地の市区町村への変換には国土地理院への通信を使う。

## 3. 入力：UI/app.py

画面でアレルギー、地域、日程を選ぶ。アレルギーは未設定でも使える。

画面は元の5つの表示欄と4つのチェック項目を使い、検索前も未取得として表示する。現在地・保存設定と、取得後の種類別情報は折りたたんで確認する。取得条件に合う対策文は「からだケアのアドバイス」へ表示する。

初回表示で`call_api()`が`GET /api/v1/locations/options`へ問い合わせ、地域一覧を`st.session_state`へ保持する。都道府県を選ぶと、その都道府県の市区町村だけを表示する。都道府県を変えたら市区町村は未選択に戻す。「花粉・気象と対策を取得」を押したときだけ予報を取得し、選択欄や対策チェックを操作しただけでは取得し直さない。

画面はStreamlitの仕組みにより、操作のたびにPythonコードが再実行される。`st.session_state`は、その間も選んだ地域や取得した結果を保持するためのもの。ブラウザーを閉じた後まで結果を保存する機能ではない。

## 4. 現在地と保存：UI/browser.py、UI/state.py、UI/browser_component/index.html

現在地の取得とブラウザー保存は、ブラウザー側のJavaScriptが行う。Pythonだけで本人の位置許可画面を出すわけではない。

- `browser.py`：JavaScriptの画面部品をStreamlitへ組み込む。
- `index.html`：位置の取得、localStorageへの設定保存・読み出し・削除を行う。
- `state.py`：届いた通知を確認し、設定やメッセージをPython側へ反映する。

現在地の座標が届くと、UIは通信制御の現在地用の窓口へ送る。通信制御が市区町村と代表地点を決め、UIは都道府県と市区町村の両方を選択済みにする。以降の取得は、手動選択した場合と同じ自治体IDを使う。

次回まで保存するのはアレルギー設定だけ。現在地・APIキー・判定結果は保存しない。

## 5. 受付：server/api.py

HTTPで届いた依頼を、URLと操作の種類で振り分ける。

| 依頼 | 行き先 |
| --- | --- |
| 都道府県・市区町村の選択肢 | `Locations.catalog()`（自治体コード順に全件） |
| 市区町村名の検索（互換用。現在の画面では不使用） | `Locations.search()` |
| 現在地から市区町村を特定 | `Locations.current()` |
| 気象・花粉と対策の取得 | `Controller.recommend()` |

HTTPの受信・JSONの読み取り・返信の共通部分は`common/http_api.py`にある。

## 6. 地域の確定と結果の集約：server/controller.py、server/locations.py

`Controller.recommend()`には、自治体ID、対象日、アレルギー設定が届く。

1. `common/protocol.py`で入力の形式・日付・設定を確認する。
2. `Locations`で自治体IDから代表地点の緯度・経度を取得する。
3. `MqttCollector.collect()`で気象と花粉へ取得を依頼する。
4. 返信の日付とエラーを確認する。
5. 正常な取得結果とアレルギー設定を推薦担当へ送る。
6. 推薦の結果を画面へ返す。

検索ごとに`request_id`を付け、別の検索の返信が混ざらないようにする。

## 7. 取得依頼と返信：common/mqtt_transport.py

このファイルには、通信の両側を担当する2つのクラスがある。

- `MqttCollector`：通信制御側。依頼を送り、気象・花粉の返信を集める。
- `Worker`：取得担当側。依頼を受け、取得関数を呼び、結果を返信する。

`on_connect`、`on_subscribe`、`on_message`は、MQTTライブラリが接続・購読・受信時に呼ぶ関数。これをコールバックという。普通の関数の上から下への実行に加え、メッセージが来たときに呼ばれる処理がある。

待機期限、同時実行の上限、重複防止もここにある。最初は「依頼→取得関数→返信」の経路を押さえ、その後で待機や重複防止を読む。

## 8. 気象・花粉の取得

`weather/worker.py`と`pollen/worker.py`の`main()`が、デモ用の取得関数か実API用の取得関数を選び、`Worker`へ渡す。

気象の実API経路：

```text
Worker
  → get_weather(request)
  → weather_data_output(緯度, 経度, 対象日)
  → Open-Meteo
  → 返ってきたJSONから指定日の値を取り出す
  → 通信で使う項目名へ合わせて返す
```

花粉の実API経路：

```text
Worker
  → get_pollen(request)
  → get_pollen_info(緯度, 経度, 対象日)
      → get_pollen_data()でAPIからJSONを取得
      → format_pollen_data()で対象日・種類別の値へ整理
  → 結果を返す
```

デモではこの実API経路を通らず、`common/providers.py`の`mock_data()`を使う。

一括起動では、`run.py`が`weather.worker`、`pollen.worker`、`server.api`を直接起動する。これらと同じ処理を呼ぶだけの旧入口4ファイルは、2026-10-19の不要物整理で削除した。担当別に起動するときも、READMEにある各モジュールを使う。

## 9. 対策の判定：recommend/api.py、recommend/service.py

`recommend/api.py`で受け付け、`assess()`で判定する。

1. 入力と設定を確認する。
2. 取得できた種類と取得できなかった種類を分ける。
3. 設定種の最大UPIを使う。未設定なら地域分類の最大UPIを使う。
4. UPI 0〜1は低、2〜3は中、4は高、5は非常に高いとする。
5. 対策文を選ぶ。風や雨は対策を追加するが、花粉レベルを上げない。
6. 画面へ返す結果を作る。

設定種が一部取得できなければ暫定、全て取得できなければ個人レベルは判定不可。樹木全体の値をスギの値として代用しない。

`assess()`には将来のAI用の引数があるが、現在のHTTP受付では渡していない。通常起動でGeminiへ対策文を生成させる実装にはなっていない。

`recommend/recommend.py`は元の推薦コードで、現在の`service.py`からは天気の表示・分類や対策文の確認などの関数を使う。現在のHTTP経路の中心は`service.py`の`assess()`であり、元の`recommend()`を呼ぶ経路とは分けて読む。

## 10. 返信と表示：UI/app.pyへ戻る

結果の辞書は、画面へ返す1つのまとまり。その中の役割は次の通り。

| 項目 | 意味 | 例 |
| --- | --- | --- |
| `data` | 画面に表示する要約 | 地域、日付、レベル、持ち物・行動 |
| `details` | 取得した詳しい値 | 種類別UPI、気象の値、地域の参考値 |
| `meta` | 結果をどう作ったか・判定の状態 | デモか、暫定か、使えた設定種 |
| `errors` / `warnings` | 取得失敗や注意 | 花粉未取得、デモ用の架空値 |

`meta`は「メタデータ」の略で、この結果についての付帯情報。別のDBではない。

整理後の`assess()`では、要約を`display_data`、詳しい値を`details`、判定状態を`metadata`として別々に作り、最後に1つの辞書へまとめて返す。通信で使う`data`・`details`・`meta`という名前は変えていない。

UIは結果を`st.session_state`へ保持し、カード・数値・チェック項目・種類別表を描く。これで1回の検索が終わる。

## 検証範囲

書き方の整理前後で全体テスト154件が成功。推薦の修正前後の結果は1,620通りで一致。Chromiumで市区町村検索、実HTTP/MQTTを通すデモ表示、対策チェック、設定保存・復元・削除、東京駅の検証用座標からの市区町村取得、位置許可拒否後の手動検索を確認した。

実Google花粉、本人の実GPS、他ブラウザー、複数PC、実Geminiは今回の確認に含めていない。
